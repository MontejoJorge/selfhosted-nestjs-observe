# apps/web — agent guide

Vite + React 19 dashboard for the self-hosted `@nestjs/observe` collector. It only reads the
query API (`/api/*`) served by `apps/api`. Repo-wide rules live in the root [AGENTS.md](../../AGENTS.md).
Load the `react-best-practices` and `composition-patterns` skills before writing code.

## Stack

| Concern      | Library                                                                     |
| ------------ | --------------------------------------------------------------------------- |
| Routing      | React Router v7, data mode (`createBrowserRouter` + `RouterProvider`)       |
| Server state | TanStack Query (`queryOptions` factories, loaders warm the cache)           |
| HTTP client  | Generated by swagger-typescript-api (axios) from `apps/api/openapi.json`    |
| Search state | URL search params parsed with zod                                           |
| UI           | Tailwind CSS v4 (`@tailwindcss/vite`) + shadcn/ui (radix base, nova preset) |
| Charts       | Recharts through shadcn's `ChartContainer` (`src/components/ui/chart.tsx`)  |
| Icons        | lucide-react                                                                |

Maintainer decisions: React Router (data mode) for routing, TanStack Query for all server state,
and the generated API client for every HTTP call.

## Generated API client

`src/lib/api/generated/api.ts` is generated from the committed `apps/api/openapi.json` by
`pnpm --filter web api:client`, which `dev`, `build` and `typecheck` run first. Root
`pnpm api:generate` rebuilds the spec from the API and then the client. Methods are grouped by
resource and return the body directly, e.g. `api.requests.listRequests(query, { signal })`.
Import DTO and enum types (`RequestDetailDto`, `TimeRange`, `LogLevel`, ...) from
`@/lib/api/generated/api`. Never redeclare API types; ask the backend owner to change the spec.

## Conventions

- **Data flow.** Components never call `api` (or axios/fetch) directly. Each feature exposes
  `queryOptions`/`infiniteQueryOptions` factories in `features/<area>/queries.ts` that call `api`
  and pass the query's `signal`. Query keys start with the area and include the scope and filters,
  e.g. `['requests', 'list', scope, filters]`.
- **Loaders prefetch only.** In `router.tsx` each route's `loader` parses the request URL and calls
  `queryClient.ensureQueryData(...)` (or `ensureInfiniteQueryData`) and returns nothing. The
  component reads the same factory with `useSuspenseQuery` / `useSuspenseInfiniteQuery`; never use
  `useLoaderData`. Page components are code-split with `lazy`.
- **Loading and errors.** `HydrateFallback` covers the first load, `AppShell` shows a pending bar
  from `useNavigation()`, and a pathless route with `ErrorBoundary: RouteError` renders page errors
  inside the shell (404 from the API or a missing param shows the not-found page).
- **Scope.** Everything telemetry lives under `/projects/:projectId` (slug or id). `useScope()`
  returns `{ project, application, range }`, whose names match the API's query params, so a
  Scope spreads straight into a call. `application` and `range` are global search params: link
  with `ScopedLink` / `useScopedNavigate` so they are kept across navigation. The only ranges are
  1h, 24h and 7d (maintainer decision).
- **Search params.** Page filters (`operationId`,
  `status`, `level`, `q`, ...) have a zod schema in `features/<area>/search.ts`, used by the loader
  (`parseRequestSearch`) and the page (`const [filters, setSearch] = useTypedSearch(schema)`;
  `setSearch({ key: undefined })` removes a key). Free-text inputs use `DebouncedInput` so typing
  doesn't navigate on every keystroke. The API rejects unknown query params, so only send
  documented ones.
- **Units.** Durations are ms, rates are 0..1 ratios, runtime memory is MB, `cpuPercent` is percent
  of one core, `eventLoopUtilization` is 0..1, GC fields are per bucket.
- **Empty states.** Every list handles "no data" with `EmptyState`; when nothing matches without
  filters, include `NoTelemetryHint` (tells the user to point `OBSERVE_ENDPOINT` here).
- **Look.** Dark first (light kept working). Cards are `Panel`s; tables go in `TableFrame` (mono
  UPPERCASE headers); filters are dashed `FilterChip`s; detail pages use `KeyValueList`. Show
  only what the API really returns: compute from existing endpoints or ask the backend, never
  fake a figure. Mutations use `mutationOptions` factories from `queries.ts` and `toast` (sonner).
- **Composition.** Prefer small composable components (`PageHeader` + `PageTitle`, `StatGrid` +
  `Stat`, `KeyValueList` + `KeyValue`) and explicit variants over boolean props. Keep hooks and
  constants out of component files (fast refresh), e.g. `use-sorted-rows.ts`, `theme-context.ts`.
- **Charts.** One y-axis per chart (split measures into separate charts). Colors come from the theme
  tokens in `src/index.css` (`--chart-1..5`, `--status-ok|warn|error`, `--span-db|http|code`), which
  have light and dark values. Status colors always come with an icon or label.
- **Links.** Table rows are real links: put `<ScopedLink className={stretchedLink}>` in one cell of a
  `LinkRow`; other links in the row need `relative z-10`.
- **shadcn/ui.** Add components with `pnpm dlx shadcn@latest add <name>` from `apps/web`. Do not
  hand-write them.
- **Tests.** Vitest (`vitest.config.ts`, which reuses `vite.config.ts` and pins `TZ=UTC`). Specs are
  co-located `*.spec.ts` files (`*.spec.tsx` for hooks); a spec covering several sibling modules sits in
  their parent folder (`features/search-schemas.spec.ts`). Pure modules run in node; hook specs start
  with `// @vitest-environment jsdom` and render the hook with `@testing-library/react` under a
  `createMemoryRouter`. Test `lib/` helpers, the zod search schemas and the `*-math.ts` modules; do not
  test shadcn/ui components or mock the generated client.
- Everything in English.

## Add a page

1. Add the query factory in `src/features/<area>/queries.ts` (stable key, `api.<resource>.<method>`
   in `queryFn` with `{ signal }`).
2. If the page has filters, add a zod schema in `src/features/<area>/search.ts`.
3. Build the page in `src/features/<area>/<name>-page.tsx`: `useScope()`, `useTypedSearch(schema)`,
   `useSuspenseQuery(factory(...))`, `Page`/`PageHeader`/`PageTitle`, and an `EmptyState`.
4. Add the pathname to `src/lib/paths.ts` and a route object in `src/router.tsx` under the pathless
   error-boundary route: a `loader` that calls `ensureQueryData` and
   `lazy: async () => ({ Component: (await import('...')).MyPage })`.
5. Add a nav entry in `src/components/layout/app-nav.tsx` if it is a top-level area. Only add
   entries for pages that exist (no placeholders).

## Commands

```sh
pnpm --filter web dev          # http://localhost:5173 (the API's CORS default allows this origin)
pnpm --filter web build        # api:client, tsc -b, vite build
pnpm --filter web typecheck
pnpm --filter web lint         # oxlint
pnpm --filter web test         # api:client, then the unit tests (Vitest); test:watch to re-run on change
pnpm --filter web api:client   # regenerate src/lib/api/generated from apps/api/openapi.json
```

## Demo mode

`--mode demo` (`.env.demo`: `VITE_DEMO=true`) runs the dashboard with no backend: `main.tsx` starts a
Mock Service Worker (`src/demo/`) that answers every `/api/*` call with generated telemetry before the
router is created. `src/demo/world.ts` defines the fictional projects, apps, operations, jobs, errors and
releases; `store.ts` generates the history and keeps extending it; `handlers/` mirrors the query API. When
the API adds or changes an endpoint, update its handler. Normal builds never include `src/demo` or MSW.

```sh
pnpm --filter web dev:demo       # dev server on generated data
pnpm --filter web build:demo     # static build in dist-demo/ (deployable to any static host)
pnpm --filter web preview:demo
```
